## Binding decisions (user decisions from feature-forge workshop)

1. **v2.1.0 Scope:** Four major features in one ambitious milestone:
   - Full 3D ASCII content set (all entities re-authored as detailed 3D models)
   - Day/night lighting cycle (turn-based progression)
   - Signed installers + SBOM (production-ready distribution)
   - Orbitable 3D camera (debug-key gated: configurable, default Ctrl+Shift+C)

2. **Model Detail Level:** High detail — 5+ primitives per entity with animations:
   - Trees: trunk cone + canopy ellipsoid + branch cylinders + root capsules
   - Buildings: wall boxes + roof ellipsoid + door cylinder + window boxes + chimney capsules
   - NPCs/Player: torso box + head sphere + hat cylinder + limb capsules (arms/legs) + walk cycle animation
   - Props: multi-primitive compositions with idle animations (e.g., water surface ripple)

3. **Timeline:** 3-4 months for ambitious scope

4. **Camera Access:** Debug key only (configurable, default Ctrl+Shift+C) — not available to regular players by default

5. **Time Progression:** Game turns = hours (each turn advances time; night cycle every N turns)

6. **Animation Determinism:** Frame timing uses fixed-point arithmetic (integer ticks per frame) to guarantee cross-platform determinism.

7. **Cache Frame Deduplication:** Identical animation frames share cache entries via content hash; `animation_frame` in `CacheKey` is a frame content hash, not a frame index.

8. **Night Ambient Fill:** Default 0.15, user-adjustable in Settings (0.15–0.30); contrast tests verify WCAG AA ≥ 4.5:1 for all primary glyphs at minimum ambient.

9. **macOS Notarization Fallback:** If notarization times out after 20 min, attach unsigned DMG with clear warning label; schedule re-signing in next patch release.

10. **Save Migration Default:** v2.0.x saves load with `time_of_day = 120` (noon), not midnight.

11. **PingPong Single Frame:** `LoopMode::PingPong` with 1 frame behaves as static (same as `Loop`).

## One-paragraph summary

This spec defines v2.1.0 of Dust Trail: an ambitious milestone delivering four major features. The full 3D ASCII content set re-authors every game entity as detailed 3D primitive models (5+ primitives each) with walk-cycle and idle animations, replacing the minimal v2.0.0 model set. A day/night lighting cycle advances with game turns, modulating the single directional light's angle and intensity and adding ambient fill light at night. Signed installers (Windows MSI, macOS DMG, Linux .deb/.AppImage) with minisign signatures and a CycloneDX SBOM are produced by CI. An orbitable 3D camera (rotation, zoom, perspective toggle) is available behind a debug key (Ctrl+Shift+C) for testing and advanced users. All features maintain headless testability and the clean-room, no-crash discipline of v2.0.0.

# Section 2 — Overview and user value

## What the player experiences after this milestone

The player launches Dust Trail and finds a world where every tree, building, character, and prop is a shaded 3D ASCII sculpture with genuine volume and animation. Trees sway gently; NPCs walk with visible limb movement; water ripples; buildings show architectural detail. As the game progresses through turns, the sun arcs across the sky — shadows lengthen, colors shift from warm noon to cool dusk to dark night with a soft ambient glow, then brighten again at dawn. The lighting change is visible on every 3D surface. For advanced users, pressing Ctrl+Shift+C unlocks a fully orbitable camera: rotate the view with mouse drag, zoom with scroll, toggle between isometric and perspective projection. The distribution artefacts are production-signed installers with verified signatures and an SBOM for supply-chain transparency.

## Why it matters

v2.0.0 proved the 3D ASCII pipeline works end-to-end with a minimal model set. v2.1.0 fulfills the visual promise: a world where every object reads as a 3D form, not a flat glyph. Animations make the world feel alive. Day/night cycles create atmosphere and tactical variation (night favors stealth; day favors visibility). Signed installers + SBOM establish Dust Trail as a professionally distributed application. The debug camera enables content authoring, debugging, and advanced play without cluttering the default experience. Together, these features transform Dust Trail from a "tech demo of 3D ASCII" into a visually complete, professionally distributed game.

## What is explicitly NOT in it

- Multiplayer / networking
- Commercial-licence assets or trademarked names
- Pixel-copying of any commercial product
- Dynamic weather (rain, fog, snow) — deferred to v2.2.0
- Procedural model generation — models are hand-authored in v2.1.0
- Camera collision with geometry — orbitable camera clips through objects in debug mode

## Data flow (extended from v2.0.0)

```
Game state (domain) → TimeOfDay (turn counter → hour, light dir/intensity/ambient)
                          → object selection (visible entities/tiles)
                            → model lookup (registry: entity kind → ObjectModel + animations)
                              → animation controller (entity kind + state → current frame)
                                → cache lookup (SpriteCache keyed by model+light+size+orientation+anim_frame)
                                  → cache hit: reuse cached Sprite
                                  → cache miss: rasterise animated primitives → Sprite → store in cache
                                → depth-aware composite (Sprite → Frame/Cell with z-compare)
                              → Frame
                                → egui GUI rendering (debug camera OR fixed camera)
```

## Frame write path (unchanged from v2.0.0)

`Game::frame()` builds the frame as today, with the addition that each animated entity queries its animation controller for the current frame before cache lookup. The composite writes each sprite into the frame with depth-aware occlusion. Debug camera (when active) provides the projection instead of the fixed camera.

## Time-of-day calculation

```
const TURNS_PER_HOUR: u32 = 10;          // configurable
const TURNS_PER_DAY: u32 = 24 * TURNS_PER_HOUR; // 240 turns = 1 day

time_of_day = (turn_count % TURNS_PER_DAY) / TURNS_PER_HOUR;  // 0..23

light_elevation = sin((time_of_day / 24.0) * 2π) * 90°;       // -90° (midnight) to +90° (noon)
light_azimuth   = (time_of_day / 24.0) * 360°;                  // 0° (midnight/North) to 360°
light_intensity = max(0.0, sin(light_elevation)) * 1.0 + 0.15; // 0.15 ambient at night, 1.15 at noon
ambient_fill    = if light_elevation < 0° { 0.15 } else { 0.0 };
```

# Section 5 — Interface contracts

All signatures are Rust-like text (not compiled). Errors use `Result` where fallible; unknown/model-missing cases never panic.

## Animation

```rust
#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub enum AnimKey {
    Walk,
    Idle,
    Attack,
    Death,
}

pub struct Animation {
    pub frames: Vec<AnimFrame>,  // each frame = per-primitive transform deltas
    pub frame_duration: u32,     // turns per frame
    pub loop_mode: LoopMode,
}

#[derive(Clone, Copy, PartialEq, Eq)]
pub enum LoopMode {
    Loop,       // walk, idle
    Once,       // attack, death
    PingPong,   // sway, ripple
}

pub struct AnimFrame {
    pub primitive_deltas: Vec<PrimitiveDelta>, // indexed by primitive order in model
}

pub struct PrimitiveDelta {
    pub translation: (f32, f32, f32),
    pub rotation: (f32, f32, f32),
    pub scale: (f32, f32, f32),
}

pub struct AnimationController {
    current_anim: Option<AnimKey>,
    frame_index: usize,
    frame_timer: u32,
}

impl AnimationController {
    pub fn new() -> Self;
    pub fn set_animation(&mut self, key: AnimKey, model: &ObjectModel);
    pub fn tick(&mut self);           // advances frame_timer; loops per anim config
    pub fn current_frame(&self) -> Option<&AnimFrame>;
    pub fn is_animating(&self) -> bool;
    /// Returns per-primitive transforms for the current frame (base + delta)
    pub fn get_primitive_transforms(&self, model: &ObjectModel) -> Vec<Transform>;
}
```

Contract: `tick()` advances frame based on `frame_duration` using fixed-point arithmetic (integer ticks per frame, no floating-point); `LoopMode::Loop` wraps; `LoopMode::Once` stops at last frame; `LoopMode::PingPong` reverses direction at ends (with 1 frame, behaves as static/Loop). Unknown `AnimKey` → no animation (returns base transforms). Deterministic: same turn count → same frame (cross-platform guaranteed via integer-only frame timing).

## TimeOfDay

```rust
pub struct TimeOfDay {
    pub turn_count: u64,
    pub turns_per_hour: u32,
    pub turns_per_day: u32,
}

impl TimeOfDay {
    pub fn new(turns_per_hour: u32) -> Self;
    pub fn advance_turn(&mut self);
    pub fn hour(&self) -> u8;                    // 0..23
    pub fn light_elevation_deg(&self) -> f32;    // -90.0..=90.0
    pub fn light_azimuth_deg(&self) -> f32;      // 0.0..360.0
    pub fn light_intensity(&self) -> f32;        // 0.15..1.15
    pub fn ambient_fill(&self) -> f32;           // 0.0 or 0.15
    pub fn light_dir_normalized(&self) -> (f32, f32, f32); // for Rasteriser
    pub fn is_night(&self) -> bool;              // elevation < 0
    pub fn sun_moon_glyph(&self) -> char;        // '☀' or '☽'
}

impl Default for TimeOfDay {
    fn default() -> Self { Self::new(10) }
}
```

Contract: `advance_turn()` increments `turn_count` and wraps at `turns_per_day`. All getters are pure functions of `turn_count`. Deterministic: same turn_count → same outputs.

```rust

All state persisted in GUI settings (not save file). Toggle key configurable in Settings.

# Section 6 — Functional requirements (EARS format)

Each requirement is numbered `FR-###` and written in EARS style: "When <condition>, the system shall <action>."

## Full 3D Content Set

FR-100. When the game loads, the system shall have a detailed `ObjectModel` (5+ primitives) registered for each entity kind: tree, shrub, cactus, rock, water, barn, house, saloon, sheriff office, player, sheriff, deputy, outlaw, horse, loot chest, loot item, sign, fence, barrel, crate, well, wagon.

FR-101. When an entity is rendered, the system shall use its detailed model from the registry, not the placeholder (unless the kind is unregistered).

FR-102. When a model is defined, the system shall include appropriate materials (albedo, shade_side) for each primitive to create visual variety.

## Animations

FR-103. When an entity moves, the system shall play its `Walk` animation (4-frame cycle, limb rotation + torso bob).

FR-104. When an entity is stationary, the system shall play its `Idle` animation (subtle sway/ripple, PingPong loop).

FR-105. When an entity attacks, the system shall play its `Attack` animation once (Once loop mode).

FR-106. When an entity dies, the system shall play its `Death` animation once and then remove the entity.

FR-107. When the animation controller ticks, the system shall advance the frame timer and interpolate between keyframes based on `frame_duration`.

FR-108. When the cache is queried for an animated entity, the system shall include the animation frame content hash in the cache key so different visual frames are cached separately; identical frames (e.g., PingPong reversal) share the same cache entry.

FR-109. When an animation frame's content hash changes, the system shall miss the cache and rasterise the new frame; the previous cache entry remains valid for other entities using the same frame.

## Day/Night Cycle

FR-110. When a turn advances, the system shall increment the turn counter and update the `TimeOfDay` state.

FR-111. When the turn counter reaches `turns_per_day`, the system shall wrap to 0 (new day).

FR-112. When the time of day changes, the system shall compute the directional light elevation, azimuth, intensity, and ambient fill from the turn count.

FR-113. When the light elevation is below 0° (night), the system shall set ambient fill to 0.15 and directional intensity to 0.15.

FR-114. When the light elevation is above 0° (day), the system shall set ambient fill to 0.0 and directional intensity to `sin(elevation) + 0.15`.

FR-115. When the light elevation is near 0° (dawn/dusk), the system shall increase shadow softness (wider penumbra in rasteriser).

FR-116. When the GUI renders the toolbar, the system shall display a sun (☀) or moon (☽) glyph plus the current hour (0-23).

FR-117. When the inspector panel is open, the system shall display the exact time of day (e.g., "14:00" or "02:00").

FR-118. When the viewport renders, the system shall show a sky gradient background that shifts with time of day (blue day → orange dusk → dark night → pale dawn).

FR-120. When the release workflow runs on a version tag, the system shall build macOS DMG, codesign the app bundle, and submit for notarization (wait for completion).

FR-121. When the release workflow runs on a version tag, the system shall build Linux .deb and .AppImage, and sign both with dpkg-sig and minisign respectively.

# Section 7 — Non-functional requirements

NFR-201. Performance budget: animated sprite rasterisation shall complete in under 2 ms per object on the primary platform's CI runner; full frame with cached animated sprites shall composite in under 8 ms.

NFR-202. Cache-hit budget: on a steady-state repaint with no world/animation change, at least 85% of object sprites shall be served from cache (animations reduce cache hit rate slightly vs v2.0.0).

NFR-203. Determinism: given identical world state, time, light, camera, and animation frame, the system shall produce byte-identical sprite grids and depth maps across runs.

NFR-204. Headless testability: the animation controller, TimeOfDay, and debug camera logic shall be tested without any GUI dependency or display.

NFR-205. Memory bound: the `SpriteCache` shall hold at most `max_entries = 5000` (tunable via config); animated frames use content-hash deduplication so identical frames share entries; total memory shall not exceed 200 MB on primary platform; LRU eviction logs when triggered.

NFR-206. Accessibility — keyboard: all new features (day/night UI, debug camera toggle) shall be operable from the keyboard; debug camera toggle uses configured key (default Ctrl+Shift+C, no mouse required to enable).

NFR-206b. Accessibility — contrast: at minimum night ambient fill (0.15), all primary entity glyphs shall meet WCAG AA contrast ratio ≥ 4.5:1 against the viewport background; ambient fill user-adjustable in Settings (0.15–0.30).

NFR-207. No GUI dependency in core modules: `animation.rs`, `time.rs`, `model.rs` (extensions), `raster.rs` (extensions) shall not import egui/eframe.

NFR-208. No crash discipline: public API functions shall not use `panic!`, `unwrap`, `expect`, `unreachable!`, `todo!`, or `unimplemented!` (guide §2.6 and CI lint rule).

NFR-209. Saturation: all animation frame arithmetic, turn counter arithmetic, and angle calculations shall use checked or saturating operators.

NFR-210. Installer verification: the update-check crate shall verify minisign signatures on `SHA256SUMS.txt` before offering installers; verification failure shall fall back to "Open release page" only.

NFR-211. macOS notarization: CI shall wait for notarization to complete (polling with timeout) before attaching DMG to release.

# Section 10 — Data and state model

## Save format version vs app version

- The app Cargo version moves to `2.1.0` for this milestone.
- `SaveData.version` records `env!("CARGO_PKG_VERSION")` at save time, e.g. `"2.1.0"`.
- The on-disk JSON save format gains one new field: `time_of_day: u64` (turn count at save time). This field is optional with default 0 for backward compatibility.
- `SoundSettings` serialization unchanged (relies on `#[serde(default)]`).

## What changes and what does not

- Changes: app version string bumped to 2.1.0; `SaveData` gains `time_of_day` field; `migrate()` extended to recognize `2.1.` prefix.
- Does not change: the JSON field set for world, player, NPC, item, slot, turn, sound_settings; `SoundSettings` serialization.

## How `migrate()` is extended

Current `migrate()` keys off version prefixes `0.`, `1.0.`, `1.1.`, `2.`. The v2.1.0 extension:
- Adds a branch for the `2.1.` prefix that applies no field changes (2.1.x saves are current).
- Keeps the existing `0.` / `1.0.` / `1.1.` / `2.` branches unchanged so v1.x and v2.0.x saves still migrate.
- For any other prefix (unknown future version), applies no field changes and relies on `#[serde(default)]` for missing keys (loads with safe defaults; `time_of_day` defaults to 0).

## Backward compatibility rules

- A v1.x save file must load and produce a playable game.
- A v2.0.x save file must load in v2.1.0 without migration changes (time_of_day defaults to 120 → noon).
- A v2.1.0 save file must load in v2.1.0 without migration changes.
- The on-disk format must NOT: add required fields without defaults, remove fields, rename fields, or change the `version` field semantics.

## How rendering is asserted (no pixel baselines)

Rendering is asserted on structural properties only:
- The character grid (`cells`) — non-empty for a real model, correct glyph placement, monotonic glyph ramp.
- The depth map (`depth`) — identical dimensions to cells, nearest-wins semantics, farther cells not overwritten.
- Structural properties — byte-identical output across two runs (determinism), placeholder for unknown model, empty sprite for empty model.
- Animation properties — frame advance follows `frame_duration`, loop modes respected, interpolated transforms applied.
- NEVER a golden PNG or pixel-baseline comparison (per guide II.30.8: no pixel baselines, they fail on font-metric changes).

# Section 13 — Risks and mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Content authoring bottleneck (21 models × 5+ primitives + animations) | Delays v2.1.0 by weeks | Time-box model authoring to 2 weeks; use simple placeholders first, iterate detail |
| Animation cache explosion (each frame = separate cache entry) | Memory > 200 MB | `max_entries = 5000` (tunable); frame deduplication via content hash (identical frames share entry); LRU eviction logs; profile in CI |
| macOS notarization flakiness (Apple service delays) | Release pipeline stalls | 20 min timeout; fallback: attach unsigned DMG with warning label, schedule re-sign in next patch |
| Debug camera input conflicts with GUI shortcuts | Ctrl+Shift+C may conflict | Toggle key configurable in Settings (default Ctrl+Shift+C); handler returns `true` to consume input |
| Day/night lighting makes some glyphs unreadable at night | Accessibility regression | Ambient fill default 0.15, user-adjustable 0.15–0.30 in Settings; contrast test AC-216b verifies WCAG AA ≥ 4.5:1 for all primary glyphs at minimum ambient |
| CI release workflow duration (signing + notarization + SBOM) | > 60 min pipeline time | Parallelize OS builds; notarization in background; cache cargo-cyclonedx |
| Animation determinism across platforms | Float differences cause frame drift | **Fixed-point arithmetic (integer ticks per frame) in AnimationController**; cross-platform determinism test in CI |
| Model registry size (21 models × animations) | Binary size increase | Models are data-only; primitives are small structs; < 1 MB impact |

# Section 14 — Open questions for the owner

Exactly the questions that need the owner's answer. Recommended answer given first for each.

**Decided via spec updates (binding decisions 6–11):**
- Animation determinism: fixed-point arithmetic (integer ticks)
- Cache frame deduplication: content hash (identical frames share entry)
- Night ambient fill: default 0.15, user-adjustable 0.15–0.30 in Settings

**Remaining questions:**

1. **Turns per hour:** Is 10 turns/hour (240 turns/day) the right pace, or should it be faster/slower for gameplay feel? Recommended: 10 turns/hour (day/night cycle completes in ~20 min of active play).

2. **Walk cycle frame count:** 4 frames per cycle, or 6-8 for smoother motion? Recommended: 4 frames (classic ASCII aesthetic; 6+ frames increases cache entries significantly; frame deduplication mitigates).

3. **Debug camera default enabled:** Should debug camera be off by default (as specified) or on? Recommended: off by default (clean default experience).

5. **Notarization staple:** Should the DMG be stapled after notarization? Recommended: yes (xcrun stapler staple) so offline verification works.

6. **SBOM format:** CycloneDX JSON or XML? Recommended: JSON (smaller, easier to parse).
